## 측정 과정에서 바로잡은 점

초기 실행은 Windows venv 실행기의 메모리만 측정해 약 4MiB로 잘못 집계했다.
별도 PID 실험으로 실행기와 실제 Python의 PID가 다른 것을 확인했다.
감독 도구를 하위 프로세스 추적·트리 종료로 수정하고 실제 Python 종료 회귀 테스트를 추가한 뒤,
**새 디렉터리에서 전체 행렬을 재실행한 결과만 위 표와 JSON에 수록했다.** 제품 코드 수정은 없다.
메모리 한도 단위 테스트는 sampler 값을 주입해 감독 동작을 검사한다. 의도적인 시스템 RAM 고갈 실험을 한 것은 아니다.

## 해석과 남은 검증

이 합성 범위에서는 유한 한도·동시 2건·출력 상한·취소/timeout 보호가 동작했다.
전체 5125파일이 약 1MB이고, 32MiB 사례는 대부분 주석이므로 복잡한 실제 코드의 AST·매크로 부하를 대표하지 않는다.
이전 54.526초는 C 컴파일과 겹친 별도 실행이어서 이번 5초대 관측과 조건이 다르다. 제품 속도가 개선됐다는 뜻이 아니다.

- Windows 로컬 단일 실행, 적은 반복 수, OS 파일 캐시 효과와 다른 앱 부하를 통제하지 않았다. p95/장기 누수·SLA 보장은 없다.
- 동시 2건을 넘는 부하, 수시간 안정성, 실제 고객 대형 소스, 다른 PC/OS, CT 실행·RTE wiring·실시간 UI 응답성은 미검증이다.
- 확장 캐시 효과를 제외하기 위해 매 조회를 새 엔진 프로세스로 실행했다.
- 이번에는 기존 전체 Python/확장 Host 테스트를 재실행하지 않았다. 제품 코드·UI·의존성 변경이 없는 검증 도구 추가다.
- 후속 구현을 한다면 실제와 비슷한 함수/분기/매크로 밀도의 합성 데이터와 단계별 프로파일링부터 진행한다.
  인덱스·증분 파싱·캐시 변경은 이 테스트 요청에 포함하지 않았다.
