# 출처 흐름 UI 및 호출자 역추적 검증 — 2026-11-15 (KST)

기본 화면을 전체 카드 나열에서 **선택 후보 경로 + 선택 단계 코드**로 바꿨다.
값 경로와 조건 입력을 분리하고, 함수 안의 전달을 접어 볼 수 있게 했다.
호출부 인수, 함수 반환값, RTE 공급자 구간을 표시한다. 실제 실행 순서를 확정하지 않는다.

Windows x64 / Python 3.14.3 / Node 22.23.4 / VS Code 1.145.2.
새 의존성 없음. npm ci --offline --no-audit --no-fund로 확장 환경을 구성했다(157패키지).
Computer Use는 사용하지 않았다.

개발 Host 초기 실행 한 번은 알림 응답 대기 상태에서 중단했다. 테스트 오류를 UI 대신 전달하는 테스트 전용 포트,
이전 fixture 파일 감시 이벤트 안정화 대기, 교체한 패널의 dispose 경계 보호 후 재실행했다.
최종 VSIX Host 첫 시도는 같은 Caller_Raw가 추가 Getter 호출부에서도 발견되어 테스트가 다른 출처를 고르는 문제가 있었다.
함수/변수/위치로 Caller_Run 쪽 입력을 지정하도록 테스트를 바로잡아 전체 3단계를 다시 통과했다.
이는 새 Getter 호출부를 숨기거나 엔진 후보를 제거한 것이 아니다.

### 상호작용 검증 범위

Node VM의 작은 DOM 대역에서 **실제 배포용 inline script**를 실행했다.
갈림길/조건 진입·복귀/같은 함수 내부 단계 선택/검색/전체 보기/상태 복원을 검사했다.
동일 입력으로 더 짧게 연결되는 다른 호출부가 있어도 사용자가 선택한 앞 경로를 유지했다.
일반 화면은 선택 코드 하나만 만들고 전체 목록은 한 번에 최대50개로 제한했다.
선택 범위의 UTF-16 강조(한글·emoji 앞부분 포함), 소스 escape·CSP·오프라인/오래된 화면의 액션 차단을 확인했다.

실제 VS Code Host에서는 두 번째 매개변수와 다른 이름의 전달 인수, 반환값 인수의 실제 호출부 이름,
조건 전용 입력 분리, 소스 이동과 이력 무변경을 확인했다.
미리보기의 조작은 로컬 화면 상태이며 Python 재조회/이력 쓰기를 만들지 않는다.
소스 열기/선택 지점 추가는 기존 토큰·ID allowlist와 소스/현재 조사 검증을 통과해야 한다.

호출부 예시는 Caller_Run 쪽 Caller_Raw를 미리 고른 읽기 전용 HTML도 만들었다.
Caller_Check ← Caller_Relay ← Caller_Run의 3구간이며, 화면에서 다른 호출부로 바꿀 수 있다.
함수명이 같은 것만 보지 않고 인수 순서로 대응한다. 999/7/123 등 첫 번째 인수는 pedal의 출처로 섞지 않았다.
Caller_GetRaw()를 인수로 전달한 경우 실제 호출부 Caller_FromFunction과 반환값 제공 함수 Caller_GetRaw를 구분한다.
코드 주변 문맥은 표시 전용이며 기존 이동/저장 범위를 넓히지 않는다. 너무 긴 문맥은 정확한 기존 snippet으로 돌아간다.

### 큰 예시의 해석 정정

513지점 그래프에 포함된 g_Stimulus_000 입력 후보는 **조건 쪽 경로**였다.
값/조건을 분리해 보니 `(uint16)(...)`가 미해결 호출 후보로 남아 값 자체의 전역 입력 후보는 확인되지 않았다.
새 UI는 조건 입력을 값의 공급자로 바꾸어 보여주지 않는다. 타입/캐스트 해석 확대는 이번 UI 작업에 포함하지 않았다.
이전 TRACE-001 보고서에도 이 구분을 추가했다.

최신 실제 엔진 요청: 5125파일에서 7.778초, 프로세스 트리 메모리 집계 107.73MiB,
381059바이트 응답. 513지점/718연결·잘림 없음이며, 기본 값 경로는 42구간에서 미해결에 도달한다.
이 값은 단일 로컬 관측이며 성능 보장이 아니다. 지원 후보 그래프 탐색 완료와 값의 완전 해석을 구분한다.
